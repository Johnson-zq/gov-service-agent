# F13-Preview Confirmed Business Materials Demo

已确认事项材料展示。

F13-Preview 只在 F12 本轮首次成功产生 `confirmed_business_id` 之后，用该编号读取现有受控业务数据，把事项规范名称和现有公开材料规则允许展示的办理材料，追加到本轮回复文本。它不重新判断事项。

## 1. 背景

F12 已经关闭。它解决的是“用户要办理哪个事项”，终点是 `confirmed_business_id`。Golden 路径上这个编号是 `DEMO_SS_001`。

阶段性演示如果只说事项已确认，用户还看不到要准备什么。F13-Preview 补上这一段展示：自然语言咨询、多轮确认、最终事项、办理材料。它不是完整的政务办事知识助手。

资源门已确认：已确认编号可从 `artifacts["f10"]` 经既有读取方式取得；规范名称和材料都在 `data/demo/demo_ss_001.json`；查询可以按编号确定性完成；包装现有办理流程在技术上可行，且可以只在首次确认时触发。具体类名、文件和接线留给技术设计。资源门建议的包装方式只是实现方向，不是本需求冻结的实现细节。

## 2. Feature 目标

当且仅当本轮是首次确认时，系统展示：

- 事项规范名称
- 现有公开材料规则允许公开的办理材料名称

展示使用确定性模板。材料事实只来自受控业务数据。

当前 Golden 数据里，公开材料名称是“身份证”。需求不增加数据里没有的材料。

## 3. 与 F12 的边界

F12 保持 CLOSED。本需求不重新打开 F12 的需求、技术设计或代码。

F13-Preview 不得改变：

- F06 检索权限
- F09 槽位映射权限
- F04 确定性图推进
- F10 终点确认
- `confirmed_business_id` 的含义
- F11 会话语义

它只消费 F12 已经产生的结果。

架构口号仍然是：语义检索找方向，业务图谱定事项，规则引擎做终审，知识图谱查办理信息，Agent 统一编排。本 Preview 没有实现业务知识图谱。它复用已有受控业务数据：已确认事项编号到确定性查询，再到公开材料。不是用户原话到检索，再到猜测材料。

## 4. 数据与事实来源

已确认编号存放在 `artifacts["f10"]`，由既有 F10 读取方式取得。Golden 值为 `DEMO_SS_001`。

规范名称来自受控业务数据的 `canonical_name`。当前名称是“灵活就业人员社会保险费申报缴费”。不得用检索标题、模型改写、图上的临时文案或用户口中的名称代替它。

材料来自同一受控数据的材料记录。展示文本使用现有公开名称字段。当前数据中的字段是 `source_text`。当前 Golden 只展示“身份证”。不得改写成数据没有支持的句子，例如要求携带原件和复印件。

材料是否可公开，只由既有公开材料规则决定。当前这条规则的入口是既有 `is_public_material`，或与之等价的现有公共过滤合同。Preview 不得复制第二套核验规则，也不得自行规定 `SOURCE_EXPLICIT`、`SYSTEM_DERIVED`、`TO_CONFIRM`、`VERIFIED` 谁可以公开。它只消费过滤后的结果。

禁止用模型补材料、用检索寻找材料真相、从事项名称反推材料、从测试名称或常识补材料。数据里只有“身份证”，演示就只展示“身份证”。

展示顺序遵循现有公开查询的返回顺序。Preview 不另做优先级、模型排序或语义重排。也不另定语义去重；查询返回什么，就按什么展示。将来的数据清洗不属于本需求。

内部字段不得出现在用户回复中，包括材料编号、核验枚举、来源编号、来源文件、栏目、推导说明、置信度、图节点、候选编号和已确认编号。

## 5. 首次确认触发语义

调用 F12 办理流程之前，从恢复状态读取 `before_confirmed_id`。成功返回之后，从本轮结果状态读取 `after_confirmed_id`。

只有 `before_confirmed_id` 为空，并且 `after_confirmed_id` 非空，才是首次确认。

以下情况都不展示材料：

- 尚未确认事项
- 仍在追问槽位
- 解释请求
- 低置信
- 回退或暂不支持
- 确认准备
- 用户拒绝或确认含糊
- 进入本轮之前已经确认
- 之后的普通用户轮

查询键只能是确认之后的 `confirmed_business_id`。

## 6. 正常展示行为

有公开材料时，保留 F12 原回复，空一行，再追加：

```text
办理事项：<canonical_name>
需要准备的材料：
1. <material source_text>
2. <material source_text>
```

不得替换 F12 原回复。不得使用“全部材料如下”“仅需以下材料”“材料已经完整”“保证可以办理”“材料齐全即可办理”“只有这些材料”“无需其它材料”。这些结论没有数据合同支持。推荐用语是“需要准备的材料：”。

## 7. 无公开材料行为

事项记录存在，规范名称可读，但公开过滤后材料为空。这包括材料记录都存在、却没有一条通过公开规则的情况。

这是预期的空结果，不是系统失败，也不是确认失败。F12 确认仍然成功。不得把本轮判失败，不得清掉已确认编号，不得编造材料。

展示为：

```text
<原 F12 回复>

办理事项：<canonical_name>
当前暂无可展示的办理材料信息。
```

## 8. Preview 查询失败行为

F12 已经成功确认，但 Preview 自己的查询失败。失败包括仓库异常、事项记录意外不可用、Preview 数据无法读取，以及已确认编号在受控仓库中找不到。找不到时不得猜测名称或材料。

Preview 失败不得使成功确认失效。不得清空已确认编号，不得改写业务状态，不得伪造材料。用户至少仍看到 F12 原来的成功回复。日志和可观测性留给技术设计，本需求不新造日志机制。

## 9. F12 基础失败行为

如果 F12 办理流程本身失败，Preview 不得吞掉异常，不得把它改成成功，不得构造材料回复，不得伪造已确认编号。失败语义保持 F12 和 F11 原有合同。

两类失败必须分开：Preview 自己的失败要放过已经成功的确认；F12 的失败要原样传出。

## 10. 状态与权限边界

Preview 不是新的业务权威。它不能确定、改变或确认事项，不能改图、改槽位或判断资格。

对办理状态只读。不得修改已填写槽位、当前图节点、图转移、候选事项、已确认事项、`f09`、`f10` 或决策图。默认不新增新的权威业务材料。允许改变的只有本轮返回给用户的回复文本。

相同的已确认编号、业务数据快照和公开材料规则，必须得到相同的名称、材料事实和顺序。不允许模型随机性或检索结果波动。

Preview 使用当前运行时的业务数据快照。不新增数据库同步、远程指南刷新或自动网页更新。以后数据版本变化不属于本需求。

## 11. Session / API 边界

F11 继续负责会话锁、幂等、检查点恢复、成功提交、审计和公开响应。Preview 不直接写 Redis，不自己提交检查点，不实现第二套幂等或锁，也不自己构造公开响应模型。

相同会话、相同请求编号、相同原文的重放，仍由 F11 保证不产生第二次业务效果。Preview 不另做幂等。

检查点仍只保存 F12 产生的业务状态。材料展示不是新的检查点真相，也不能用来决定事项是否已确认或图是否前进。

审计所有权仍属 F11。Preview 不新建用户原文日志、模型回复日志或敏感材料日志。若最终回复文本按 F11 既有行为进入审计，沿用现有合同。

继续使用 `POST /api/v1/session/turn`。请求和响应字段不变。Preview 只增强 `response_text`。不新增材料、事项名称、候选编号、已确认编号、核验状态或来源编号等公开字段。不新增 `/materials`、`/business-knowledge`、`/preview` 或其它端点，也不新增端口。

生产会话路径必须在不改 F12 核心职责的前提下应用 Preview。怎么接线由技术设计决定。

## 12. 非功能要求

Preview 是非权威的展示增强。它自己的故障不得破坏已确认事项。F12 基础故障仍按原机制失败。

不新增公司模型调用、向量模型加载、语义检索、外网访问、数据库结构或端口。材料读取应是本地确定性查询这一级的轻量操作。本需求不规定没有依据的毫秒时限。

不得破坏现有 F12 Golden 流程、会话接口、健康检查、F11 幂等、办理状态持久化，以及现有 F06、F09、F04、F10 测试。

Preview 不需要接口密钥或用户身份证号。它只读取公共办事数据，不在回复里输出内部来源、核验元数据或调试轨迹。

## 13. OUT OF SCOPE

不包含办理地点、办理渠道、办理条件、法律依据、办理时限、费用、咨询电话、大厅导航、导航图、业务知识图谱引擎、政策百科、通用知识问答、同一会话改办事项、语音识别、前端、微信接入、自动填表或 RPA。

仓库里即使已经有地点、渠道或依据数据，也不进入本需求。本需求只做规范名称和材料。

## 14. Golden Demo

第 4 轮，用户说“无雇工的个体工商户”。候选事项是 `DEMO_SS_001`，已确认编号为空。不展示材料。

```text
办理事项：灵活就业人员社会保险费申报缴费
需要准备的材料：
1. 身份证
```

名称和“身份证”都来自现有受控业务数据。

若下一轮用户再说“好的”或“谢谢”，进入本轮前已确认编号已经非空，不得再次追加完整材料列表。
